## 3. What was built

| Component | Responsibility |
|---|---|
| `domain/parsing.py` | Pasted text → ordered turns; joins wrapped lines, infers speaker roles |
| `application/dto/analysis_schemas.py` | The five layer schemas, **built from the loaded taxonomy and rubric** |
| `application/use_cases/analyze_transcript.py` | The pipeline: parse → redact → L1–L3 → validate → score → L4–L5 → persist |
| `infrastructure/llm/prompts/l1..l5*.md` | Five versioned prompts |
| `infrastructure/persistence/tables.py` | 7 tables; findings as rows, narrative as JSON |
| `repositories/analysis_repository.py` | Atomic save, full reconstitution |
| `POST /api/v1/analyses` | The contract the Analyze and Call detail screens are built against |
| 2 Alembic migrations | First schema, then the §4 fix |

**The most consequential design choice: schemas are generated from configuration.**
Every vocabulary-constrained field becomes a `Literal` of the configured values, so
the JSON Schema sent to the provider *enumerates* the seven categories, the
sentiment states, the signal codes and the rubric dimensions. Because all three
providers constrain decoding to the schema, the model is not asked to use the
vocabulary — it cannot emit anything else. Adding a category to `taxonomy.yaml`
changes what the model may answer with no code change, which is what DEC-02
promised.

**Failure policy.** L1–L3 produce the classification and the score, so losing one
means there is no analysis: the request fails and nothing is stored. L4 and L5 are
additive; if one fails the call is still scored and stored, and that layer is
marked *unavailable with a reason*. An unavailable layer is never presented as an
empty one — the same principle as the L5 panel showing a missing trigger as a
finding.

## 4. Defect found by the live run, and fixed

The first live analysis of Call #89 — a call with **no broker** — stored a broker
attribution:

```json
{ "broker_name": "None", "issue": "No broker was mentioned by the member.",
  "evidence_turn_seq": 0, "quote": "None" }
```

The model had no broker to report and filled the fields with the literal string
`"None"`. My guard required the evidence fields to be **present**; `"None"` is a
non-empty string, so it passed.

This is the highest-risk record in the system — it names a real person, and
Compliance reviews it. P1 made an unevidenced attribution impossible to
*construct*; it did not make a *fabricated* one impossible to store.

**Fix:** broker evidence is now checked against the transcript exactly as a score
marker's is — the quoted words must genuinely appear in the cited turn. Discarded
attributions are recorded in `rejected_attribution_notes` rather than dropped
silently, so a model that keeps inventing them is visible.

One rule, not a blocklist of placeholder words: `"None"` fails because it does not
appear in turn 0, which is the same reason any other fabrication fails.

Verified against the live model: the attribution is now discarded with
*"Attribution to 'None' quotes text that does not appear in turn 0"*, and zero
broker signals are stored.

A second, smaller defect: the autogenerated migration for the new column added a
`NOT NULL` field with no `server_default`, which would have failed on any database
with existing rows. Corrected before applying, and verified against the row that
was already there.

## 5. Model quality: the finding that matters most

The **machinery** works. The **local 7B model's judgement does not**, and the gap
is large enough that it must not be discovered during a demo.

Two runs of Call #89, same model, same transcript:

| | Score | Tier | Category | Resolution | Sentiment |
|---|---|---|---|---|---|
| **Corpus (authored)** | 36 | POOR | Coverage & Benefits | UNRESOLVED | WORRIED → DISMISSED |
| Run 1 | 74 | AVERAGE | Provider Network | RESOLVED | SATISFIED → NEUTRAL |
| Run 2 | 48 | POOR | Pharmacy | RESOLVED | SATISFIED → SATISFIED |

Three separate problems:

1. **Classification is wrong.** Neither run picked the right category, and both
   called an unresolved patient-safety call RESOLVED. A member who was steered
   away from emergency care was recorded as SATISFIED.
2. **Output varies run to run.** Same input, same model, scores 74 and 48. DEC-03
   guarantees *same markers → same score*, and that holds exactly. It does not
   guarantee *same transcript → same markers*, because that depends on the model.
   **The determinism claim is narrower than it may have sounded, and this is the
   evidence.**
3. **Judgement is inverted in places.** Run 1 scored the cost-steering line as a
   *positive* compliance marker, and "No, that's all" as positive resolution
   ownership.

**What did work, on every run:** the clinical-risk signal was detected, the gate
fired, and the score was withheld pending clinical review. The single most
important safety behaviour in the product survived a model that got most of the
rest wrong — which is precisely the argument for the rubric and gates being
deterministic code rather than model output.

The evidence validator also earned its place: it rejected a fabricated marker
quote in run 1 and the fabricated broker in both.

**This is a model-selection problem, not an architecture problem**, and it is what
the P8 fidelity report exists to quantify. But it is now urgent rather than
academic (§7).

## 6. Performance

**4 minutes per call** on `qwen2.5:7b-instruct` (2,880 input + 1,273 output tokens
across five sequential calls). Extrapolated to the P7 corpus run: **~6.5 hours for
100 calls sequentially.** Concurrency will reduce wall-clock but not GPU time.

This makes the corpus run an overnight job on this hardware unless a faster model
or a cloud provider is used, and it should shape how P7's UI-triggered run is
presented — a progress bar over six hours is a very different thing from one over
six minutes.

## 7. Decisions and open questions

| # | Decision | Reasoning |
|---|---|---|
| P3-1 | Layer schemas built from config, not hard-coded | Constrained decoding enforces the vocabulary; adding a category needs no code change |
| P3-2 | L1–L3 fatal, L4–L5 degrade | A call without a category or score is not an analysis; a call without an L4 finding still is |
| P3-3 | Broker evidence validated like marker evidence (§4) | Both name things a human will act on; there is no reason for the weaker rule |
| P3-4 | Findings stored as rows, narrative as JSON | P4 aggregates across calls; unpacking JSON per row would be unqueryable |
| P3-5 | Stored taxonomy **codes**, resolved on read | Renaming a label updates every stored call; a missing code raises rather than rendering a mystery string |
| P3-6 | Turn indices are the evidence anchor | The UI highlights from stored indices, not by searching text in the browser |

**Now urgent — the Ollama model choice.** `qwen2.5:7b-instruct` is not good enough
for this task on the evidence above. Three options, and I would like your steer:

1. **Try the larger local models already installed** (`llama3.1:latest`,
   `qwen2.5-coder:14b`) — free, slower, unknown quality.
2. **Point the corpus run at a cloud provider.** Far better judgement and much
   faster; needs a key, and means synthetic transcripts leave the machine.
   *(The corpus is synthetic, so this is a cost decision, not a privacy one — but
   it would make the "nothing leaves this environment" claim false for that run.)*
3. **Tune the prompts first** and re-measure — some of the classification error
   may be recoverable with sharper instructions.

My recommendation is **(3) then (1)**, with (2) held for the demo run if the local
results stay poor. Either way, P8's fidelity report over all 100 calls is what
should settle it, and this argues for pulling that measurement earlier.
