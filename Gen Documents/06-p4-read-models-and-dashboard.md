## 2. Exit criterion

> *Integration tests assert every dashboard figure against a known fixture database.*

**Met.** `tests/support/corpus.py` defines eleven calls whose expected figures a
reader can verify by hand from the specs; `test_dashboard_read_models.py` asserts
every figure against them. The fixture is deliberately shaped so each definition
has something to prove:

- Two agents above the significance threshold and one below it.
- All four resolutions present, so a first-contact-resolution figure that quietly
  counted partials would be visibly wrong (36.4% correct vs 54.5% if inflated).
- One broker net positive, one not.
- An L4 category with no signals at all.
- One call raising two findings in the same L4 category, so calls-not-signals
  counting is testable.

## 3. What was built

| Component | Responsibility |
|---|---|
| `domain/aggregation/statistics.py` | Median, mean, percentages, histogram binning |
| `domain/aggregation/attention.py` | The attention queue: rules, evaluation, ranking |
| `config/dashboard.yaml` | Histogram bins and the attention rules, as configuration |
| `application/ports/read_models.py` | The aggregate rows the dashboard is built from |
| `repositories/read_models.py` | SQL grouping and counting, filters applied before paging |
| `application/use_cases/get_dashboard.py` | Overview, agent performance, broker scorecard, signal distribution |
| `GET /dashboard/{overview,agents,brokers,signals}` | The four dashboard views |
| `GET /calls`, `GET /calls/{id}` | Filterable, paginated list and full detail |
| `GET /taxonomy` | Vocabularies, so the frontend hard-codes nothing |

**The split that matters:** SQL groups and counts; the domain does the
arithmetic. Every definition — median, FCR, histogram bins, tier, significance —
is a pure function testable without a database, and each is defined exactly once.

**Nothing on the attention queue is written by a model.** The prototype's queue
makes book-level claims ("13 of 16 prior auth calls unresolved"); a claim like
that is either counted or invented, and only the counted version can be acted on.
Titles and narratives are templates filled from counts.

Three counting rules are enforced and each is easy to get subtly wrong:

- **L4 categories count calls, not signals** — a call with two compliance
  findings is one call with a compliance problem.
- **Broker signals count signals, not calls** — the scorecard tallies what
  members reported.
- **Filters apply before paging** — so the total is the number of matching calls,
  not the size of a page.

## 4. Defects found and fixed

**1. An attention rule fired on the wrong signal.** `signal_present` rules had no
way to name *which* signal they watched, so the clinical-risk rule matched a
**disclosure** problem and headlined it "Agents are not escalating clinical
urgency". A dashboard that puts the wrong headline over real counts is worse than
one showing nothing. Rules now declare `applies_to`, and the loader cross-checks
it against the taxonomy — the same guard the rubric gates already have, because
it is the same failure mode: silent, visible only as an item that stopped
appearing.

**2. A migration would have silently destroyed data.** Moving signal codes from a
JSON column to a table, the autogenerated migration dropped the column without
moving the data. Worse, my first fix *looked* correct but did nothing: the patch
script used `str.replace` without verifying the match, the anchor had shifted, and
it reported success anyway. The column was dropped with the data in it.

The root cause of the third attempt failing was subtle and worth recording: on
SQLite, `batch_alter_table` **drops and recreates** the parent table, and with
`PRAGMA foreign_keys=ON` that drop fires the child's `ON DELETE CASCADE` — wiping
rows written moments earlier. The migration now reads the data into memory first,
rebuilds the table, creates the child table, and only then writes. Proven lossless
in **both directions** on a scratch database, and the two affected dev rows were
restored.

**3. The dependency rule was broken.** `get_dashboard.py` imported
`HistogramSettings` from `infrastructure.config.dashboard_loader` — the
application layer reaching into infrastructure. Caught by the import-linter
contract, not by review. The settings describe the histogram, not the file they
are loaded from, so they moved into `domain/aggregation/statistics.py`.

That contract has now earned its place twice over: it caught a violation I did
not notice while writing the code.

**4. Tests were running against a schema-less database.** Earlier phases only
needed `SELECT 1`, so no fixture created tables. Fixed, and — because tests now
build the schema from ORM metadata for speed while production uses Alembic —
`tests/audit/test_schema_matches_migrations.py` runs the real migrations and
compares. Without it, a green suite could be proving a schema that exists nowhere.

## 5. Decisions taken during P4

| # | Decision | Reasoning |
|---|---|---|
| P4-1 | One `dashboard.yaml` rather than the plan's `attention_rules.yaml` | Histogram bins and attention rules are both "how the dashboard is computed" and change together |
| P4-2 | Signal codes normalised into `call_signals` | The prototype's Calls screen filters by signal; filtering a JSON array means dialect-specific SQL or filtering after pagination, which breaks the total |
| P4-3 | Rules declare `applies_to` (§4.1) | Without it a rule matches every group of its kind |
| P4-4 | Empty categories and owners returned with a zero count | "Provider relations has no signals in this sample. Shown so the absence is visible rather than implied." |
| P4-5 | Calls sorted by severity, not date | The prototype's stated rule; withheld scores first, then lowest scores |
| P4-6 | `GET /taxonomy` exposes the vocabularies | The frontend renders filters from it, so adding a category reaches the UI with no frontend change — the other half of DEC-02 |

## 6. Verified live

Against the real database holding the two Call #89 analyses from P3:

```
calls 2 | median 61.0 mean 61.0 | FCR 100.0 %
provisional 2 | brokers 0 | taxonomy coverage 100.0 %
attention: CRITICAL | Agents are not escalating clinical urgency
           | owner Quality and Clinical | refs ['C0001', 'C0002']
```

The clinical-risk item fires on both real calls, correctly owned and referenced.

**The 100% FCR is worth reading carefully.** The model marked both Call #89 runs
RESOLVED — a call where a member was steered away from emergency care. The
dashboard is faithfully reporting what is stored. This is P3 §5's model-quality
problem surfacing exactly where it will be most visible to a stakeholder, and it
is the strongest argument yet for resolving the model question before any demo.

## 7. Open questions

**Unchanged and now more pressing: the model choice** (P3 §7). P4 makes the
consequence concrete — a wrong resolution does not stay in one call's detail
page, it becomes the headline metric on the Overview screen. My recommendation
remains: tune the prompts, re-measure, and hold a cloud provider for the demo run
if local results stay poor.

Two smaller items, neither blocking:

1. **Attention thresholds** in `dashboard.yaml` are set for a 100-call corpus. On
   a real month of several thousand calls they need raising — which is why they
   are configuration.
2. **The prototype's Overview shows a "last 30 days" filter.** The API has no
   date filtering yet. Worth adding in P6 if the screen keeps that control.
